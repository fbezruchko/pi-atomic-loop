# Loop-модуль — Документация

> **Основная документация (английский): [DOCUMENTATION.md](DOCUMENTATION.md)** — это русская версия-альтернатива; английский файл является авторитетным.

Необслуживаемый loop-режим для [pi](https://github.com/earendil-works/pi): вы даёте агенту **одну цель**, а он работает над ней небольшими итерациями — часами или днями — пока **вы** его не остановите. Работает с коммерческими моделями (Claude, GPT, Gemini) так же, как и с открытыми (Qwen, GLM, gpt-oss, …), потому что сам цикл hardened против типичных слабостей слабых моделей: зацикленность на повторениях, ложные «готово», сбои провайдера.

## 1. Установка

Из git (рекомендуется сейчас):

```bash
pi install git:github.com/fbezruchko/pi-atomic-loop@v1.0.6
```

Или из локального клона:

```bash
pi install /path/to/pi-atomic-loop
```

Затем перезагрузите pi или выполните `/reload`. Команда `/loop` станет доступна.

## 2. Быстрый старт

**Рекомендуемый workflow — цель, подготовка, запуск (отдельные фазы с выбором модели):**

```text
/loop goal Собрать REST API для управления задачами в ./taskapi: CRUD, auth, SQLite, тесты, docs. Коммитить инкрементально в git.
/loop prepare --model anthropic/claude-opus-4-6     # сильная модель пишет GOAL.md + check.sh
/loop run --model vllm-omega/qwen3-coder-30b        # дешёвая/локальная модель работает по циклу
```

**Или всё в один шаг** (без подготовки, с текущей моделью):

```text
/loop start Собрать REST API для управления задачами в ./taskapi: CRUD, auth, SQLite, тесты, docs. Коммитить инкрементально в git.
```

**Наблюдение:**

```text
/loop status
```

**Остановка:**

```text
/loop finish   # мягкая: дождаться окончания текущей итерации, затем остановить
/loop stop     # жёсткая: прервать текущий turn
```

**Продолжение:**

```text
/loop resume
```

Этого достаточно для базовой работы.

### Трёхфазный workflow в деталях

| Фаза | Команда | Что происходит | Типичная модель |
|-------|---------|--------------|---------------|
| **1. Установка цели** | `/loop goal <goal> [flags]` | Сохраняет цель + конфигурацию. **Ничего не запускает.** | — (без вызова LLM) |
| **2. Подготовка** (опционально) | `/loop prepare [--model M] [--quick]` | Модель обсуждает с вами план (детали реализации, сложность `mvp/standard/design`, уровень модели `strong/weak` — см. skill `atom-planning`), анализирует проект и пишет `GOAL.md` (спецификация, размер атомов, вехи) плюс сценарий проверки. Завершается `GOAL_READY:`. Затем вы можете просмотреть и отредактировать `GOAL.md`. `--quick` пропускает диалог (дефолты: mvp + weak). | Сильная модель (Opus, GPT-5, …) |
| **3. Запуск цикла** | `/loop run [--model M]` | Запускает реальный бесконечный цикл. Первая итерация читает `GOAL.md` как спецификацию. | Дешёвая/локальная модель (Qwen, GLM, Sonnet, …) |

Идея: **разделить планирование и выполнение.** Дорогая сильная модель один раз пишет точную спецификацию — дешёвая или локальная модель работает по ней днями. `GOAL.md` лежит в проекте, переживает compaction/перезагрузки и упоминается в каждом loop-промпте («read it whenever you lose track of the plan»).

## 3. Основная идея

Цикл работает так (атомарные циклы разработки):

```
┌───────────────────────────────────────────────────────────┐
│ /loop goal <goal>  → задаёт цель, ничего не запускает       │
│ /loop prepare      → сильная модель пишет GOAL.md           │
│ /loop run          → один атом в СВЕЖЕЙ сессии Pi          │
└──────────────────┬────────────────────────────────────────┘
                   ▼
        ┌─── Одна сессия Pi = ровно один атом ─────────────┐
        │ 1. Свёжая сессия: чистый контекст, только          │
        │    передача состояния (loop state) + инструкция   │
        │ 2. Модель читает GOAL.md / PROGRESS.md /          │
        │    TESTMANUAL.md и работает над ОДНИМ атомарным   │
        │    заданием с фокусными тестами                   │
        │ 3. Запускается проверка цели (если --check)       │
        │ 4. Оценка:                                        │
        │    Ошибка? → повторить тот же атом (backoff)      │
        │    Повтор? → stuck-стратегия                      │
        │    Регресс? → приостановить, починить старый атом │
        │    Атом готов? → git checkpoint, сессия останавливается │
        └───────────────┬───────────────────────────────────┘
                        ▼
   supervised:  ожидание оператора (/loop resume запускает
                следующий атом в ещё одной свежей сессии)
   autonomous (--until-done): контроллер создаёт следующую
                свежую сессию Pi автоматически, пока проверка
                не пройдёт или MVP не достигнут
```

**Основные принципы:**

- **Один атом на сессию**: одна сессия Pi работает над ровно одним атомарным заданием, затем останавливается. Следующий атом получает *свёжую* сессию Pi — история разговора никогда не является долговечным состоянием, поэтому слабые/локальные модели не «плывут» на устаревшем контексте.
- **Долговечная передача**: `GOAL.md`, `PROGRESS.md`, `TESTMANUAL.md`, `ASSUMPTIONS.md`, `IMPROVEMENTS.md` плюс git-checkpoints переносят всё между сессиями.
- **Разделение планирования и выполнения**: сильная модель один раз пишет точную спецификацию (`/loop prepare`); дешёвая или локальная модель работает по ней (`/loop run`).
- **Объективная истина**: с `--check` о прогрессе и завершении решает shell-команда — не самооценка модели.
- **Персистентность**: состояние цикла хранится в записях сессии; маркер передачи свежей сессии позволяет контроллеру распознать собственные заменяющие сессии.

## 4. Референс команд

| Команда | Описание |
|---------|-------------|
| `/loop goal <goal> [flags]` | Установить цель + конфигурацию **без запуска**. |
| `/loop goal` | Показать текущую цель и конфигурацию. |
| `/loop prepare [--model M] [--file F] [--quick]` | Диалог планирования с вами (детали, уровень сложности, уровень модели), затем сильная модель пишет спецификацию (`GOAL.md`) + сценарий проверки. `--quick` пропускает диалог. |
| `/loop run [--model M]` | Запустить цикл в **свёжей сессии Pi** (чистый контекст) — опционально с другой моделью, чем для подготовки. |
| `/loop start <goal> [flags]` | Краткая форма: установить цель + сразу начать (один шаг, свёжая сессия Pi). |
| `/loop <goal>` | Короткая форма `/loop goal <goal>` — устанавливает цель и конфигурацию, **ничего не запускает**. |
| `/loop resume [--max N] [--check "CMD"] [--model M] [--rescue-model M]` | Продолжить остановленный/паузируемый цикл в **свёжей сессии Pi** (чистый контекст), опционально с новым лимитом/проверкой/моделью. |
| `/loop status` | Показать полное состояние. |
| `/loop stats` | Статистика из итерационного лога (`.pi-loop-log.jsonl`): события, интервенции, продуктивные итерации/ч, тренд score. |
| `/loop finish` | Мягкая остановка: текущая итерация завершается, затем новый turn не запускается (состояние сохраняется для `/loop resume`). Аlias: `/loop soft-stop`. |
| `/loop stop` | Жёсткая остановка: немедленно прервать текущий turn, состояние сохраняется. |
| `/loop end` | Завершить цикл и очистить состояние. |
| `/loop help` | Краткая справка. |

**Флаги** (действуют с `goal`, `start` и частично с `prepare`/`run`/`resume`):

| Флаг | Описание |
|------|-------------|
| `--max N` | Лимит итераций (дефолт: ∞). |
| `--delay S` | Пауза между итерациями в секундах. |
| `--check "CMD"` | Объективная функция цели (см. [раздел 6](#6-функция-цели---check)). |
| `--check-timeout S` | Таймаут проверки в секундах (дефолт 120). |
| `--file GOAL.md` | Имя файла спецификации (дефолт `GOAL.md`). |
| `--model M` | Модель для этой фазы: `provider/id` (например `anthropic/claude-opus-4-6`) или уникальная подстрока id (например `qwen3-coder`). |
| `--rescue-model M` | Сильнее модель, которая берёт управление на **один** turn чистки после 3 consecutivных stuck-интервенций (см. [раздел 7](#7-обработка-ошибок-и-сбоев)). |
| `--until-done` | Цикл останавливается при верифицированном завершении. |
| `--quick` | только `prepare`: пропустить диалог планирования; использовать дефолты (`Complexity: mvp`, `Model tier: weak`). |

**Синтаксис цели**: всё до `Done when:` — это цель, всё после — критерии:

```text
/loop start Реализовать фичу X. Done when: тесты зелёные и README обновлён.
```

Без `Done when:` цикл работает в чистом режиме улучшения («continuous improvement until the operator stops the loop»).

### Выбор модели (`--model`)

Каждая фаза может использовать свою модель:

```text
/loop goal Собрать X …                                  # без вызова LLM
/loop prepare --model anthropic/claude-opus-4-6       # планирование: сильная модель
/loop run --model vllm-omega/qwen3-coder-30b          # выполнение: локальная модель
```

- Формат: `provider/id` (точно) или уникальная подстрока id модели (`--model qwen3-coder` найдёт `vllm-omega/qwen3-coder-30b`).
- Модель, выбранная на `run`, сохраняется как **loop-модель**: после перезагрузки pi auto-resume восстанавливает её (с предупреждением, если её нет — тогда цикл продолжается на текущей модели).
- Неизвестная модель или отсутствующий API-ключ → чёткое сообщение об ошибке, цикл **не** запускается.
- Без `--model` фаза просто использует текущую активную модель.
- Переключение в середине: `/loop stop`, затем `/loop resume --model <другая модель>`.

### Модель спасения (`--rescue-model`)

Сильно рекомендуется для длинных запусков со слабых/локальных моделей:

```text
/loop run --model vllm-omega/qwen3-coder-30b --rescue-model anthropic/claude-sonnet-4-5
```

Если loop-модель 3 раза подряд застревает, модель спасения берёт управление ровно на **один turn**: она inspects состояние проекта, доводит одну конкретную вещь, переписывает `PROGRESS.md` (следующие 3 однозначных шага с путями файлов), обновляет backlog `IMPROVEMENTS.md` и оставляет строку `NEXT:`. Затем цикл продолжается на обычной модели — слабые модели лучше следуют чёткому внешнему плану, чем создают его сами.

### Подготовка (`/loop prepare`)

`/loop prepare` отправляет однократное задание модели (не loop!):

0. **Диалог планирования** (skill `atom-planning`): модель обсуждает с вами — уточняющие вопросы об реализации (по одному), затем два обязательных вопроса: ожидаемая сложность решения (`Complexity: mvp | standard | design`) и класс модели, который будет реализовывать атомы (`Model tier: strong | weak`). Tier лишь определяет размер атомов (strong → крупные связные атомы, weak → крошечные микро-атомы); он никогда не меняет `--model`. Пропустить можно `--quick` (дефолты: mvp + weak).
1. Просмотреть состояние проекта (файлы, README, тесты).
2. Написать `GOAL.md`: строки `Complexity:` / `Model tier:` сразу под «## Original User Request», раздел **Atom sizing** с выбранным зерном, уточнённой целью, scope & non-goals, измеримыми критериями завершения, roadmap из маленьких шагов, стандартами качества (тесты, docs, git-commits), явными допущениями.
3. Если объективно проверяемо: создать сценарий проверки (`check.sh`) и упомянуть его в `GOAL.md`.
4. Завершиться `GOAL_READY: <summary>` — по этому extension понимает, что подготовка готова, и рекомендует точную команду `--check`.

После этого: **посмотреть `GOAL.md` и отредактировать его вручную при необходимости** — только `/loop run` запускает цикл. Отныне loop-промпт упоминает спецификацию в каждой итерации; первая итерация явно начинается с чтения `GOAL.md`.

## 5. Опции в деталях

### `--max N` — лимит итераций

Дефолт: **безлимитный** (∞). С `--max 50` цикл паузит после 50 итераций. `/loop resume` продолжает — если лимит исчерпан, автоматически переключается на безлимитный (с заметкой).

Полезно для: первых тестовых запусков с новой моделью, контроля расходов с коммерческими API.

### `--delay S` — пауза между итерациями

Дефолт: **0 с**. С `--delay 30` цикл ждёт 30 секунд между итерациями.

Полезно для: лимитов rate у коммерческих API, экономии ресурсов локального GPU, когда параллельно бегут другие jobs.

### `--until-done` — классический «до конца» режим

Дефолт: **выкл** (бесконечный режим). С `--until-done` цикл останавливается при завершении:

- **С `--check`**: цикл останавливается, как только команда проверки вернёт exit code 0 — *верифицированное* завершение, независимо от того, что говорит модель.
- **Без `--check`**: цикл останавливается, когда модель отчитается `LOOP_DONE:` (самооценка — ненадёжна со слабыми моделями, поэтому `--check` рекомендуется).

## 6. Функция цели (`--check`)

Функция цели — это shell-команда (выполняется через `bash -lc`), которая работает **после каждой итерации**. Это объективная функция приспособленности цикла.

### Договор

| Сигнал | Значение |
|--------|----------|
| **Exit code 0** | Критерии завершения выполнены. С `--until-done`: цикл останавливается (верифицированное завершение). |
| **Exit code ≠ 0** | Критерии ещё не выполнены. Цикл продолжается. |
| **`SCORE: <число>`** в выводе (опционально) | Числовой score прогресса, выше = лучше. Разрешены отрицательные/дробные значения. Если встречается несколько раз, считается последнее. |

### Что даёт проверке цикл

1. **Верифицированное завершение** — с `--until-done` решает exit-code, не заявление модели. Если модель отчитается `LOOP_DONE:`, а проверка провалилась, заявление отклоняется: *«Completion is decided by the check, not by your claim. Fix exactly what the check reports»* — включая вывод проверки в промпт.
2. **Обнаружение регресса** — если score упал относительно предыдущего запуска, модель сразу получает regression-промпт: посмотреть последние изменения (`git diff`/`git log`), починить регресс, прежде чем делать что-то другое. Критично для многодневных запусков, где рефакторинг тихо ломает тесты.
3. **Реальное доказательство прогресса** — новый лучший score считается измеримым прогрессом и питает no-progress аудит (см. [раздел 7](#7-обработка-ошибок-и-сбоев)).
4. **Объективная обратная связь** — каждый loop-промпт содержит текущий статус проверки:

```text
Goal check: `./check.sh` → FAILING (streak 3) · score 34 (best 41 @ iteration 87)
```

Таким образом модель оптимизирует против измеримой величины, а не против своей самооценки.

### Примеры сценариев проверки

**Простой — тесты должны пройти:**

```bash
/loop start Починить все баги в ./app. Done when: тесты зелёные --check "cd app && npm test" --until-done
```

**Со score — число прошедших тестов:**

```bash
#!/usr/bin/env bash
# check.sh — функция приспособленности для запуска сборки API
cd taskapi || { echo "SCORE: 0"; exit 1; }

# Сборка должна работать, иначе score 0
npm run build >/dev/null 2>&1 || { echo "SCORE: 0"; exit 1; }

# Score = число прошедших тестов
passed=$(npm test 2>/dev/null | grep -oE '[0-9]+ passing' | grep -oE '[0-9]+' || echo 0)
echo "SCORE: $passed"

# Готово при 50+ прошедших тестов
[ "$passed" -ge 50 ] && exit 0 || exit 1
```

**Многомерный score — тесты + покрытие − предупреждения линтера:**

```bash
#!/usr/bin/env bash
cd myproject || { echo "SCORE: -1000"; exit 1; }
go build ./... >/dev/null 2>&1 || { echo "SCORE: -1000"; exit 1; }

tests=$(go test ./... 2>/dev/null | grep -c '^ok' || echo 0)
coverage=$(go test -cover ./... 2>/dev/null | grep -oE '[0-9]+\.[0-9]+%' | tr -d '%' | awk '{s+=$1; n++} END {print (n ? int(s/n) : 0)}')
lint=$(golangci-lint run 2>/dev/null | wc -l | tr -d ' ')

score=$(( tests * 10 + coverage - lint ))
echo "SCORE: $score"

# Готово: все пакеты ok, покрытие ≥ 80%, без предупреждений линтера
[ "$coverage" -ge 80 ] && [ "$lint" -eq 0 ] && go test ./... >/dev/null 2>&1 && exit 0
exit 1
```

**Веб-проект — эндпоинты + E2E:**

```bash
#!/usr/bin/env bash
cd webapp || exit 1
npm run build >/dev/null 2>&1 || { echo "SCORE: 0"; exit 1; }
unit=$(npx vitest run --reporter=json 2>/dev/null | jq '.numPassedTests' 2>/dev/null || echo 0)
e2e=$(npx playwright test --reporter=json 2>/dev/null | jq '.stats.expected' 2>/dev/null || echo 0)
echo "SCORE: $(( unit + e2e * 5 ))"   # E2E-тесты весить больше
[ "$e2e" -ge 10 ] && exit 0 || exit 1
```

### Идеи для score

- Число прошедших тестов / E2E-тестов
- Процент покрытия тестами
- Число реализованных API-эндпоинтов (например через `grep -c 'app\.\(get\|post\|put\|delete\)'`)
- Отрицательное число ошибок: `SCORE: -$(eslint . 2>/dev/null | wc -l)`
- Чеклист фич: `SCORE: $(grep -c '^\- \[x\]' FEATURES.md)`
- Взвешенные комбинации (см. выше)

### Правила для хороших сценариев проверки

- **Держать быстрой** (< 2 мин; иначе увеличить `--check-timeout`). Проверка работает после *каждой* итерации.
- **Детерминированная**: без flaky-тестов в проверке — любой прыжок score вниз запускает regression-промпт.
- **Устойчивая**: сам скрипт никогда не должен вешаться; использовать таймауты по шагам (`timeout 60 npm test`).
- **Значимо монотонная**: score должен расти, когда продукт улучшается. Не: «число файлов» (приглашает к производству мусора).
- Если сама команда проверки падает (например, не найдена), цикл показывает предупреждение и продолжается **без блокировки**.

## 7. Обработка ошибок и сбоев

Цикл рассчитан на работу без присмотра днями. Обзор всех ситуаций:

| Ситуация | Поведение |
|-----------|-----------|
| **Временная ошибка модели/провайдера** (краш, лимит rate, таймаут, пустой ответ, `stopReason: "error"`) | Автоматический retry с экспоненциальным backoff: 5 с → 10 с → 20 с → … → макс. 5 мин. Затем «recover»-промпт: кратко сориентироваться и продолжить. |
| **Ошибка давления контекста** (`length` с ≤32 output-токенами или 400-/контекст-/токен-ошибка при ≥85% контекста) | LLM-независимая аварийная compaction, затем один recovery-turn. Разрешены две аварийные попытки; третий consecutivный сбой паузит с сохранённым состоянием, вместо вечного retry. |
| **Модель повторяет одну и ту же ответ** (сравнение fingerprint, 2× одинаково) | Stuck-интервенция: инъецируется ротативная recovery-стратегия (см. ниже), со возрастающим delay 2 с → 4 с → … → 60 с. **Никогда не паузит.** |
| **Модель повторяет почти одну и ту же ответ** (≥ 80% схожесть по word-trigram, цифры замаскированы — ловит перефразировки вроде «Already exists. Let me continue with improvements…») | Также stuck-интервенция. |
| **Одна и та же ответ 3×+ в недавнем окне** (включая чередование A-B-A-B) | Также stuck-интервенция. |
| **3 turn без единого вызова инструмента** (чистое повествование вместо работы) | Также stuck-интервенция. |
| **Дегенеративная генерация** (одно предложение ≥ 4×, одно слово ≥ 16× подряд или фраза из до 4 слов ≥ 8× подряд в *одном* ответе) | Ответ сохраняется обрезанным (гигиена контекста) + stuck-интервенция. Циклы по предложениям при стриминге прерываются при ≥ 6 повторениях; word-/phrase-забег прерываются на своих порогах. Прерывание идёт в автоматическую stuck-recovery вместо паузы. |
| **Одинаковый результат/ошибка инструмента 3× подряд** | Также stuck-интервенция. |
| **Один и тот же вопрос 2× повторён** | Также stuck-интервенция. |
| **3 consecutivные stuck-интервенции** | Эскалация hard-reset: последние начинки ответов инъецируются как запрещённые формулировки; первое действие turn **должно** быть вызовом инструмента (никакого текста до него). Если задан `--rescue-model`: вместо этого rescue-turn (см. ниже). |
| **5 consecutivных stuck-интервенций** | Auto-compaction: контекст сжимается (повторяющиеся фразы-заполнители явно исключаются из резюме), чтобы паттерн повтора вышел из окна контекста. |
| **8 итераций без конкретной изменения** (никаких write/edit файлов, никакого роста score) | Audit-промпт: «Stop analyzing, produce a tangible artifact now: a file change, a green test, a fixed bug, or a commit.» |
| **Модель отчитывается `LOOP_DONE:`** (бесконечный режим) | Цикл продолжается с «improve»-промптом: выбрать и реализовать самую ценную следующую улучшение. |
| **Модель отчитывается `LOOP_DONE:`, но проверка провалилась** (`--until-done`) | Заявление отклоняется; «check_failed»-промпт с выводом проверки. |
| **Score проверки падает** | Немедленный «regression»-промпт: посмотреть диффы, починить регресс. |
| **Проверка проходит** (`--until-done`) | Верифицированное завершение — цикл останавливается. |
| **Модель отчитывается `LOOP_BLOCKED:`** | Цикл **не** паузит. «unblock»-промпт: сделать самое разумное допущение, записать в `ASSUMPTIONS.md`, продолжить. |
| **Оператор жмёт Esc** (turn прерван) | Цикл сознательно паузит (воля оператора). `/loop resume` продолжает. |
| **`/loop finish`** (мягкая остановка) | Текущая итерация завершается, затем цикл останавливается без нового turn. Состояние сохраняется для `/loop resume`; переживает перезагрузку pi (finalized при старте сессии, а не auto-resume). |
| **Перезагрузка pi / `/reload`** | Активный цикл auto-resume через 3 с (с заметкой и возможностью отмены через `/loop stop`). |
| **`--max N` достигнут** | Цикл паузит. `/loop resume` продолжает (убирает лимит, если исчерпан). |

### Ротативные stuck-стратегии

При обнаруженном повторе инъецируется по очереди одна из этих стратегий:

1. В одной строке перечислить три действительно разных подхода, сразу выполнить наиболее перспективный.
2. Переключиться на другой подзадачу цели, к которой недавно не прикасались.
3. Написать/обновить `PROGRESS.md`: текущий статус, что было попробовано, что провалилось, следующие 3 шага — затем выполнить шаг 1.
4. Запустить сборку/тесты, починить ровно **один** сбой или предупреждение.
5. Просмотреть последние изменения (`git diff` / `git log`), проверить корректность, починить найденные проблемы.

Эта ротация предотвращает превращение самой интервенции в цикл — важно для слабых open-source моделей.

Дополнительные линии обороны против бесконечного «молчания» слабых моделей:

- **Near-duplicate-детекция**: ответы сравниваются не только точно (hash), но и по trigram-схожести (цифры замаскированы). Легко перефразированное повторение («Already exists. Let me continue with improvements…») так же ловится.
- **Обязательный инструмент**: каждый loop-промпт требует хотя бы один вызов инструмента на turn. Три turn без инструментов запускают stuck-интервенцию.
- **Эскалация hard-reset**: с третьей consecutivной stuck-интервенции последние начинки ответов передаются как запрещённые формулировки, и turn должен начинаться вызовом инструмента.
- **Kill-switch дегенерации**: если модель многократно повторяет одно предложение, одно слово 16× подряд или короткую фразу из до 4 слов 8× подряд в видимом тексте или thinking/reasoning провайдера, стрим прерывается live, ответ обрезается в сессии, и как перед каждым LLM-вызовом очищаются и текст, и thinking-контекст. Прерывание идёт в автоматическую stuck-recovery, чтобы необслуживаемый цикл продолжался, а мусор не мог самоусиливаться.
- **Сэмплинг-штрафы**: после каждой stuck-интервенции для 3 итераций устанавливаются `frequency_penalty`/`presence_penalty` (0.5) и немного повышается температура — только на OpenAI-совместимых API (vLLM, Ollama). Это борется с повторами на уровне сэмплирования, где одни промпты зачастую недостаточно.
- **Модель спасения** (`--rescue-model M`): с третьей consecutivной stuck-интервенции сильнее модель берёт один turn, чистит и оставляет чёткий план (`PROGRESS.md`, `IMPROVEMENTS.md`, `NEXT:`-строка).
- **Auto-compaction**: с пятой consecutivной stuck-интервенции контекст сжимается — свежее окно контекста часто ломает фиксации лучше любой prompt-интервенции.
- **Аварийное восстановление контекста**: при насыщении контекста loop-mode может обойти уже проваливающийся summarization-модель. Создаётся ограниченная локальная сводка из loop-state, метаданных операций с файлами и фрагментов `GOAL.md`, `PROGRESS.md`, `IMPROVEMENTS.md`, `ASSUMPTIONS.md`. Обычная Pi-compaction остаётся предпочтительным путём.
- **Circuit-breaker**: после двух аварийных recover без успешного assistant-turn третий контекст-сбой паузит цикл. После ремонта контекста `/compact`, затем `/loop resume`; обычные временные отключения провайдера сохраняют свой backoff.
- **Варьирование промпта**: «continue»-промпт слегка варьируется — одинаковые промпты стимулируют одинаковые (повторяющиеся) ответы.
- **Backlog-движимый improve-режим**: после `LOOP_DONE` в бесконечном режиме цикл работает по backlog `IMPROVEMENTS.md`: конкретные пункты с путями файлов и критерием приёмки; расплывчатые пункты («add support for other platforms») запрещены. Реализовать верхний пункт, снять галочку.

### Настройки compaction для моделей с очень большим контекстом

Дефолты Pi подходят большинству моделей. Для 512k-модели с лимитом output-токенов 65 536 и tool-тяжёлыми turnами стоит добавить проектную локальную `.pi/settings.json`:

```json
{
  "compaction": {
    "enabled": true,
    "reserveTokens": 65536,
    "keepRecentTokens": 150000
  }
}
```

Обычная compaction начнётся примерно на 87,5% загрузки, а старая часть для summarizer останется заметно ниже лимита модели. Эти абсолютные значения специфичны для окна контекста 512k. Если обычная сводка всё же проваливается, насыщенное ручное `/compact` использует локальную аварийную сводку loop-mode.

### Итерационный лог и `/loop stats`

Каждое событие цикла (continue, stuck, rescue, compact, error, done, soft_stop, …) записывается JSONL-строкой в `.pi-loop-log.jsonl` в рабочем каталоге (timestamp, итерация, event, модель, score, stuck-streak). Активный файл ограничен 5 MiB и ротится в одно `.pi-loop-log.jsonl.1`-бэкап, удерживая данные около 10 MiB. `/loop stats` читает только эти ограниченные файлы, игнорирует битые строки и сводит event-распределение, интервенции, продуктивные итерации в час и тренд score (first/best/last).

## 8. Практические примеры

> **Подсказка**: `/loop-examples [focus]` (например `/loop-examples tests`) анализирует текущий проект и предлагает готовые, подогнанные `/loop`-команды — с реальными путями, настоящими тест-/build-командами как `--check` и рекомендациями моделей для слабых моделей. Значения focus: `features`, `bugs`, `tests`, `refactor`, `docs`, `quality`.

### Пример 1: 5-дневный продуктовый запуск с разделением моделей (основной use-case)

```text
# Фаза 1: определить цель (ничего не запускает)
/loop goal Собрать production-ready REST API для управления задачами в ./taskapi (Node.js/Express, SQLite): CRUD для задач/проектов/тегов, JWT-auth, валидация, OpenAPI-документация, развёрнутые тесты. Работать в git, коммитить каждую завершённую единицу. Улучшать непрерывно: новые фичи, больше тестов, багфиксы, рефакторинг, performance. --check "cd taskapi && ./check.sh" --delay 10

# Фаза 2: сильная модель пишет GOAL.md + check.sh (~1 turn, затем GOAL_READY)
/loop prepare --model anthropic/claude-opus-4-6

# → просмотреть GOAL.md, при необходимости подкорректировать …

# Фаза 3: дешёвая/локальная модель работает днями
/loop run --model vllm-omega/qwen3-coder-30b
```

с `taskapi/check.sh`:

```bash
#!/usr/bin/env bash
cd "$(dirname "$0")" || exit 1
npm run build >/dev/null 2>&1 || { echo "SCORE: 0"; exit 1; }
passed=$(timeout 90 npm test 2>/dev/null | grep -oE '[0-9]+ passing' | grep -oE '[0-9]+' || echo 0)
endpoints=$(grep -rcE 'router\.(get|post|put|delete)' src/routes/ 2>/dev/null | awk -F: '{s+=$2} END {print s+0}')
echo "SCORE: $(( passed * 2 + endpoints ))"
exit 1   # бесконечный режим: никогда не «готово», всегда улучшать
```

Цикл бегает бесконечно, score растёт с тестами и эндпоинтами, регрессии ловятся сразу. Модель Qwen следует спецификации, написанной Opus. Через 5 дней: `/loop stop`.

**Переключение моделей в середине** (например, потому что локальная модель провалилась на вехе):

```text
/loop stop
/loop resume --model anthropic/claude-sonnet-4-5
```

### Пример 2: охота на баги до полностью зелёного

```text
/loop start Починить все проваливающиеся тесты в этом репо. Done when: вся тестовая сборка зелёная. --check "npm test" --until-done
```

Останавливается автоматически и верифицировано, как только `npm test` пройдёт с exit 0 — независимо от того, что модель говорит по ходу.

### Пример 3: поднятие покрытия тестами

```text
/loop start Поднять покрытие тестами ./src до хотя бы 90%. Писать осмысленные тесты, не мокать всё подряд. --check "./coverage-check.sh" --until-done --check-timeout 300
```

```bash
#!/usr/bin/env bash
# coverage-check.sh
cov=$(npx vitest run --coverage 2>/dev/null | grep -oE 'All files[^0-9]+[0-9]+\.[0-9]+' | grep -oE '[0-9]+\.[0-9]+' | head -1)
cov=${cov%%.*}
echo "SCORE: ${cov:-0}"
[ "${cov:-0}" -ge 90 ] && exit 0 || exit 1
```

### Пример 4: аккуратный первый запуск с новой open-source моделью

```text
/loop start Рефакторить ./legacy в TypeScript, модуль за модулем. Коммитить после каждого модуля. --max 20 --delay 15 --check "cd legacy && npx tsc --noEmit && npm test"
```

`--max 20` ограничивает тестовый запуск. Затем осмотреть результат и продолжить `/loop resume --max 100` (или без лимита).

### Пример 5: обслуживание документации за ночь

```text
/loop start Довести документацию в ./docs: каждая публичная функция документирована, примеры для всех модулей, README на актуальном уровне. Непрерывно улучшать ясность и полноту.
```

Без `--check` (качество документации трудно измерить) — no-progress аудит всё равно гарантирует, что файлы реально изменяются.

### Пример 6: погашение технического долга линтера (отрицательный score)

```text
/loop start Устранить все ESLint-предупреждения и ошибки в репо без изменения функциональности. Done when: eslint ничего не отчитывает. --check "./lint-check.sh" --until-done
```

```bash
#!/usr/bin/env bash

echo "SCORE: $(( -count ))"
[ "$count" -eq 0 ] && exit 0 || exit 1
```

Score начинается, например, с −347 и ползёт к 0. Каждая новая предупреждение (regression) сразу бросается в глаза.

## 9. Лучшие практики для многодневных запусков

1. **Работать в git-репозитории** и требовать этого явно в цели («коммитить каждую завершённую единицу»). Коммиты переживают compaction, перезагрузки и потерю контекста — и регрессии можно найти через `git diff`.
2. **Всегда использовать `--check`**, когда что-то измеримо. Функция цели — самый сильный рычаг против галлюцинаций модели.
3. **Требовать `PROGRESS.md`** — он тоже входит в правила skill. После compaction или перезагрузки модель ориентируется по нему.
4. **Устанавливать `--delay` с коммерческими API** (например 10–30 с), чтобы управлять rate-лимитами и расходами; с локальными моделями обычно 0.
5. **Первый запуск с `--max 15–25`** на неизвестной модели: осмотреть поведение, затем `/loop resume` без лимита.
6. **Формулировать цель конкретно**: технология, каталог, требования к качеству, направления улучшений. «Собери что-нибудь крутое» даёт drift; пример 1 выше — правильный уровень детализации.
7. **Учитывать песочницу**: цикл работает без присмотра с полными правами инструментов. Для длинных запусков использовать отдельный каталог/репо, желательно VM/контейнер, без доступа к production-системам.
8. **Версионировать сценарий проверки** (коммитить в репо) — тогда модель может его прочитать и понять, против чего она меряется. Но в цели чётко обозначить, что сценарий проверки нельзя манипулировать.

## 10. Отображение статуса и мониторинг

**Статусная строка** (footer, live):

```text
Loop 142/∞ · 1d 7h 23m · err 3 · score 87: Собрать в ./taskapi production-ready…
```

- `142/∞` — итерации / лимит
- `1d 7h 23m` — прошедшее время
- `err 3` — всего ошибок модели/провайдера (все автоматом пережиты)
- `score 87` — последний score проверки (или `check ✓`/`check ✗` без score)

**`/loop status`** показывает полное состояние:

```text
Active: true
Status: running
Goal: Собрать в ./taskapi production-ready REST API …
Criteria: - (endless improvement)
Mode: endless
Iterations: 142/∞
Delay: 10s
Check: cd taskapi && ./check.sh (timeout 120s)
Check status: failing (streak 2), score 87 (best 91 @ iter 138)
Goal file: GOAL.md (prepared)
Loop model: vllm-omega/qwen3-coder-30b
Rescue model: anthropic/claude-sonnet-4-5
Elapsed: 1d 7h 23m
Errors: 3 total, 0 consecutive
Interventions: 7 (stuck streak: 0)
Done signals: 2, blocked signals: 1
Last notice: -
Session entries: 4211
```

Интересные поля:
- **Interventions** — как часто нужны были stuck-/audit-/regression-промпты (высокий значение → модель борется; цель сформулировать конкретнее или выбрать сильнее модель).
- **Done signals** — как часто модель отчитывалась «готово» (в бесконечном режиме это нормально и безвредно).
- **Check status** — `streak` считает consecutivные провалы проверки; `best @ iter` показывает, когда был достигнут лучший значение.

**`/loop stats`** оценивает итерационный лог `.pi-loop-log.jsonl` (текущий запуск, иначе все запуски):

```text
Loop stats (current run, 214 entries, .pi-loop-log.jsonl):
Events: continue 187, stuck 14, done 6, rescue_start 3, compact 1, error 3
Interventions: 18 (rescue 3, compact 1)
Productive iterations/h: 11.2
Score: first 12, best 91, last 87
```

Так можно сравнивать, какая модель или формулировка цели стабильно работает (мало интервенций, высокая продуктивная скорость, растущий score). Файл лежит в рабочем каталоге — при желании внести в `.gitignore`.

## 11. Внутренности и константы настройки

Константы в начале `extensions/index.ts`:

| Константа | Значение | Значение |
|-----------|----------|----------|
| `BASE_BACKOFF_SECONDS` | 5 | Начальный backoff после ошибки модели. |
| `MAX_BACKOFF_SECONDS` | 300 | Потолок backoff (5 мин). |
| `NO_PROGRESS_WINDOW` | 8 | Итерации без конкретной изменения до audit-промпта. |
| `AUTO_RESUME_DELAY_MS` | 3000 | Время ожидания перед auto-resume после перезагрузки. |
| `MAX_STORED_TEXT` | 280 | Длина snippet для сохранённых fingerprint. |
| `SIMILARITY_THRESHOLD` | 0.8 | Jaccard-порог для near-duplicate-ответов. |
| `REPEAT_WINDOW_COUNT` | 3 | Один и тот же fingerprint N× в недавнем окне = stuck. |
| `MAX_TOOLLESS_TURNS` | 3 | Turn без вызова инструмента до stuck-интервенции. |
| `HARD_RESET_AFTER` | 3 | Stuck-streak до эскалации hard-reset. |
| `DEGENERATE_REPEATS` | 4 | Повторы предложения в одном ответе = дегенерация. |
| `DEGENERATE_STREAM_REPEATS` | 6 | Повторы предложения, с которых prерывается стрим mid-stream. |
| `DEGENERATE_WORD_REPEATS` | 16 | Consecutivные повторы одного слова = дегенерация. |
| `DEGENERATE_PHRASE_REPEATS` | 8 | Consecutivные повторы короткой фразы = дегенерация. |
| `DEGENERATE_MAX_PHRASE_WORDS` | 4 | Максимальная width токенов повторной фразы. |
| `RESCUE_AFTER` | 3 | Stuck-streak до rescue-turn (если `--rescue-model`). |
| `COMPACT_AFTER` | 5 | Stuck-streak до auto-compaction. |
| `PENALTY_TURNS` | 3 | Итерации со сэмплинг-штрафами после интервенции. |
| `LOG_FILE` | `.pi-loop-log.jsonl` | Активный итерационный лог для `/loop stats`. |
| `MAX_LOG_BYTES` | 5 MiB | Лимит на файл; сохраняется один `.1`-бэкап. |
| `CONTEXT_PRESSURE_PERCENT` | 85 | Использование контекста, с которого length-/контекст-ошибки подходят под аварийное восстановление. |
| `LOW_OUTPUT_LENGTH_TOKENS` | 32 | Максимальный output на `length`-стопе, который считается давлением контекста независимо от процента. |
| `MAX_EMERGENCY_SUMMARY_CHARS` | 24 000 | Твёрдый предел LLM-независимой аварийной сводки. |

**Как работает детекция:**

- *Детекция повтора*: SHA-256 fingerprint по нормализованному тексту ответа (убраны whitespace/ANSI, lowercase, первые 4 000 символов). Сравниваются последние 5 assistant-ответов и последние 10 результатов инструментов. Error-turns (`stopReason: error/aborted`) не включаются в fingerprint.
- *Детекция прогресса*: вызовы инструментов `write`/`edit`, ключевые слова успеха в выводе инструментов (`created`, `passed`, `committed`, …) или новый best-score проверки.
- *Персистентность*: состояние сохраняется как custom-session-entry (`loop-state`) через `pi.appendEntry()` — оно **не** попадает в контекст LLM.
- *Проверка цели*: выполняется через `pi.exec("bash", ["-lc", CMD])` с таймаутом; парсинг `SCORE:` по regex (последнее вхождение считается, разрешены отрицательные/дробные значения).
- *Гигиена контекста*: цикл инъецирует на итерацию лишь один компактный промпт (цель + правила + статус проверки) и допускает обычную compaction pi — сессия никогда не переливается полностью.

## 12. FAQ

**Почему цикл не останавливается, когда модель говорит «готово»?**
Потому что это use-case: продукт, который растёт непрерывно в течение дней. В бесконечном режиме `LOOP_DONE:` ведёт к «improve»-промпту (следующая фича, больше тестов, багфикс, …). Если нужен классический «до конца», используйте `--until-done` — желательно с `--check`.

**Модель говорит, что тесты зелёные, а их нет.**
Именно для этого нужен `--check`. Цикл верит лишь exit-code команды проверки, никогда не заявлению модели.

**Что происходит при rate-лимите в середине ночи?**
Retry с экспоненциальным backoff до макс. 5 мин между попытками, безлимитное число. Утром `err N` в статусной строке покажет, как часто было тяжело.

**Можно ли планировать и выполнять с разными моделями?**
Да — это рекомендуемый workflow: `/loop goal <goal>` (только ставит цель), `/loop prepare --model <сильная модель>` (пишет `GOAL.md` + сценарий проверки), `/loop run --model <дешёвая модель>` (работает по спецификации). Loop-модель сохраняется и восстанавливается при auto-resume после перезагрузки.

**Что происходит с GOAL.md после подготовки?**
Он лежит в проекте как обычный файл — его можно просмотреть и отредактировать до `/loop run`. Цикл упоминает его в каждом промпте; рабочая модель читает его в первой итерации и всякий раз, когда теряет нить.

**Можно ли вмешиваться, пока цикл работает?**
Да. Обычное сообщение подаётся в цикл как steering. `Esc` паузит цикл (сознательно — воля оператора), `/loop resume` продолжает. `/loop finish` останавливает gracefully после текущей итерации.

**Не «съест» ли цикл в итоге весь контекст?**
Обычная автоматическая compaction pi — основной щит. Если сама запрос суммаризации больше не влезает, loop-mode распознаёт получившуюся low-output `length`-/контекст-ошибку и делает одну ограниченную LLM-независимую аварийную compaction. Circuit-breaker паузит после повторных провалов восстановления, вместо того чтобы раздувать контекст бесконечными retry. Долгосрочная ориентация всё равно должна жить в `GOAL.md`, `PROGRESS.md` и git-истории.

**Что, если сценарий проверки сам сломан?**
Предупреждение в UI, цикл продолжается без помех (проверка никогда не блокирует). `/loop resume --check "исправленная CMD"` задаёт новую команду проверки.

**Работает ли это с локальными моделями (Ollama/vLLM)?**
Да — цикл agnostic к модели и специально hardened для слабых (детекция повторов и дегенерации, сэмплинг-штрафы, модель спасения, auto-compaction, верификация завершения через проверку, retry ошибок). Рекомендация для маленьких моделей: более конкретная цель, всегда `--check`, задать `--rescue-model <сильная модель>`, при желании `--max` для первого запуска.

**Модель постоянно повторяет одно и то же предложение, слово или короткую фразу — что делать?**
Ничего — для этого есть несколько линий обороны: near-duplicate-детекция ловит перефразировки, а kill-switch дегенерации прерывает mid-stream циклы по предложениям, забеги одного слова (16×) и короткие фразы (8×) и вырезает их из контекста. Автоматическая stuck-recovery продолжает цикл; сэмплинг-штрафы, модель спасения и auto-compaction эскалируют при необходимости. Если всё же часто случается: проверить `/loop stats` — много `stuck`/`compact`-событий указывают на слишком слабую модель или слишком расплывчатую цель.

**Как остановить всё и начать заново?**
`/loop end` полностью очищает состояние. `/loop start <новая цель>` тоже полностью заменяет цикл.
